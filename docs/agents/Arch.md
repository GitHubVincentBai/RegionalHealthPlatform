## 1. 文档概述

### 1.1 项目名称

沈阳市和平区全域综合养老服务项目（一期）区域康养平台

### 1.2 建设背景

本项目面向沈阳市和平区全域综合养老服务体系建设，覆盖 1 处龙湖邻里中心养老服务点位和 31 处社区居家养老服务点位，目标是建设统一的数智化养老服务平台，支撑老人健康监测、服务呼叫、智能安防、运营管理、家属互动和多端协同。

一期建设重点聚焦以下能力：

- 老人健康数据实时监测与管理
- 服务呼叫与响应闭环
- 智能安全监控与预警
- 养老机构与社区站点运营数字化
- 老人、家属、工作人员之间的信息协同

### 1.3 文档目标

本文档用于说明平台的一期总体架构设计，包括业务架构、应用架构、数据架构、技术架构、集成架构、安全架构、部署架构和运维保障方案，作为产品设计、研发实施、测试验证和后续扩展的统一依据。

### 1.4 设计范围

一期范围包括：

- 1 个区域级统一养老服务平台
- 1 个龙湖邻里中心业务运营支撑
- 31 个社区居家养老服务点位接入与统一管理
- Web 管理后台、移动工作端、家属微信小程序
- 穿戴设备、呼叫按钮、门禁、视频监控等设备接入

不在一期重点范围内但需预留扩展能力的内容包括：

- 政府监管平台深度对接
- 医保、医院 HIS/EMR 深度互联
- 完整 AI 模型自研平台
- 全量微服务拆分

## 2. 架构设计原则

### 2.1 总体原则

- 统一平台、分级管理：以区域统一平台支撑多站点协同，实现中心统管、站点自治。
- 业务解耦、能力复用：设备接入、告警、消息、档案、工单等公共能力平台化。
- 先易后难、分期演进：一期优先满足可上线、可运营、可扩展，后续逐步增强。
- 稳定优先、安全优先：对养老服务中的呼叫、告警、健康数据等关键链路优先保障可用性与可审计性。
- 多端协同、体验统一：统一接口规范与权限模型，支撑 Web、移动端、小程序协同。
- 数据沉淀、可分析：支持运营报表、健康趋势、告警分析、监管留痕。

### 2.2 技术原则

- 平台层与设备接入层解耦
- 业务服务与算法能力解耦
- Python 与 Go 按能力边界协同，而非重复建设
- 数据存储按数据特征选型
- 默认支持容器化部署和 CI/CD
- 默认具备可观测性、审计和配置中心能力

## 3. 总体架构

### 3.1 总体分层

平台采用“感知层 - 平台层 - 应用层 - 展示层”四层总体架构。

```text
+--------------------------------------------------------------+
| 展示层                                                       |
| Web 管理后台 | 护理/运营移动端 | 家属微信小程序 | 大屏看板    |
+--------------------------------------------------------------+
| 应用层                                                       |
| 档案管理 | 健康管理 | 服务呼叫 | 安防告警 | 运营管理         |
| 家属互动 | 消息通知 | 报表分析 | 工单中心 | 支付缴费         |
+--------------------------------------------------------------+
| 平台层                                                       |
| 统一身份认证 | 权限中心 | 主数据中心 | IoT 平台 | 事件中心      |
| 消息中心 | 文件中心 | 报表中心 | API 网关 | 集成适配层      |
+--------------------------------------------------------------+
| 感知层                                                       |
| 穿戴设备 | 呼叫按钮/主机 | 摄像头 | 门禁设备 | 定位设备        |
+--------------------------------------------------------------+
```

### 3.2 总体架构说明

- 感知层负责采集健康、呼叫、安全、门禁等现场数据。
- 平台层负责统一接入、统一身份、统一数据、统一事件和统一集成。
- 应用层负责将平台能力编排为可运营的业务系统。
- 展示层负责向不同角色提供适配终端和交互界面。

### 3.3 多站点模式

平台采用“1 个区域平台 + N 个站点”的多租户式组织管理模式，但一期不建议引入复杂 SaaS 租户隔离模型，而是采用“统一数据库逻辑隔离 + 组织/站点数据权限”的方式。

- 区域平台：负责统一档案、统一规则、统一告警中心、统一报表。
- 龙湖邻里中心：作为核心运营中心，承载机构养老、长者食堂、老年大学、中医理疗等业务。
- 社区站点：聚焦居家养老服务点位运营、社区服务联动和基础服务记录。

## 4. 业务架构

### 4.1 业务域划分

| 业务域 | 核心职责 | 主要对象 |
|---|---|---|
| 用户与权限域 | 用户、角色、组织、站点、数据权限管理 | 用户、角色、组织、岗位 |
| 老人档案域 | 老人全生命周期档案管理 | 老人、家属、床位、合同、风险等级 |
| 健康管理域 | 健康数据接入、趋势、评估、预警、报告 | 健康记录、预警规则、干预记录 |
| 呼叫告警域 | 一键呼叫、受理、分派、响应、关闭、升级 | 呼叫单、响应记录、超时规则 |
| 安防监控域 | 视频事件、跌倒识别、门禁联动、处置闭环 | 告警事件、视频记录、门禁事件 |
| 运营管理域 | 人员、排班、考勤、绩效、工单、物资、餐饮 | 员工、班次、库存、菜单、工单 |
| 财务结算域 | 账单、收费、对账、支付状态管理 | 账单、支付单、退款记录 |
| 家属互动域 | 家属端查询、通知、视频互动、反馈 | 家属账号、互动记录、通知 |
| 消息通知域 | 站内信、短信、微信、催办、预警推送 | 消息模板、发送任务、回执 |
| IoT 设备域 | 设备接入、注册、心跳、数据上报、状态监控 | 设备、设备模型、遥测数据 |
| 数据分析域 | 运营看板、服务报表、健康报表、告警报表 | 指标、统计任务、报表快照 |

### 4.2 核心业务流程

#### 4.2.1 老人建档流程

站点运营人员创建老人基础档案，绑定家属关系、站点信息、房间床位信息、服务协议和风险标签，形成完整老人主数据。

#### 4.2.2 健康数据采集与预警流程

穿戴设备或人工录入健康数据进入平台，经清洗、标准化和规则引擎处理后，生成趋势数据与预警事件，通知医生、护理员或家属。

#### 4.2.3 紧急呼叫处置流程

老人通过床头或公共区域呼叫按钮触发事件，呼叫中心获取位置、老人身份、风险等级并推送给护理站和移动端，处理完成后形成闭环记录；若超时则升级通知。

#### 4.2.4 智能安防事件处置流程

视频分析平台识别跌倒、异常聚集、闯入等事件后，通过集成适配层推送平台，由事件中心生成告警单、分派责任人并记录处置过程。

#### 4.2.5 家属信息查询流程

家属通过微信小程序登录后，可查看授权范围内的老人健康数据、护理记录、账单缴费状态、活动通知和消息提醒。

## 5. 应用架构

### 5.1 分层设计

应用架构建议按以下层次建设：

| 层级 | 说明 | 主要组件 |
|---|---|---|
| 接入层 | 面向多端与第三方提供统一入口 | Web、小程序、移动端、第三方回调 |
| 网关层 | 统一鉴权、路由、限流、日志、灰度 | API Gateway、BFF |
| 业务服务层 | 面向业务场景提供服务编排 | 档案服务、呼叫服务、运营服务等 |
| 领域能力层 | 提供可复用领域能力与规则引擎 | 预警规则、事件中心、消息中心 |
| 数据服务层 | 统一访问结构化与非结构化数据 | 数据访问服务、缓存、搜索服务 |
| 集成接入层 | 对接硬件设备和外部平台 | IoT Adapter、视频适配器、支付适配器 |
| 运维支撑层 | 保障系统运行与观测 | 配置中心、日志、监控、任务调度 |

### 5.2 推荐服务划分

一期建议采用“模块化单体 + 少量独立服务”的折中架构，既控制复杂度，又能支撑高并发链路独立扩展。

#### 核心业务服务

- `user-service`：用户、角色、组织、权限
- `elder-service`：老人档案、家属关系、床位、标签
- `health-service`：健康数据、趋势、评估、报告
- `call-service`：呼叫单、分派、闭环、超时升级
- `alert-service`：安防事件、告警聚合、事件处置
- `ops-service`：人员、排班、考勤、物资、餐饮、工单
- `billing-service`：账单、缴费、对账
- `family-service`：家属查询、互动、消息触达
- `report-service`：报表、指标、数据集市查询

#### 平台基础服务

- `gateway-service`：统一 API 网关与接入控制
- `iot-access-service`：设备注册、连接管理、消息接入
- `message-service`：短信、微信、站内消息、推送
- `file-service`：报告、图片、附件、视频截图管理
- `audit-service`：操作日志、审计留痕
- `schedule-service`：定时任务、报表任务、索引任务

### 5.3 Python 与 Go 职责分工

| 技术栈 | 优先负责能力 | 原因 |
|---|---|---|
| Python | 健康数据分析、规则引擎、报表、AI 编排、后台管理型 API | 迭代快，适合规则、数据处理、算法集成 |
| Go | IoT 接入、实时消息、呼叫高并发链路、设备网关、事件消费 | 性能稳定，适合高并发、长连接、设备接入 |

建议分工如下：

- Go 承载：设备接入网关、MQTT/WebSocket 服务、呼叫事件接入、门禁/视频事件通道。
- Python 承载：老人档案、健康管理、运营管理、账单、报表、家属服务、规则引擎。
- 二者通过 REST、消息队列或事件总线协作，避免跨服务直连数据库。

## 6. 数据架构

### 6.1 数据对象分类

| 数据类型 | 示例 | 推荐存储 |
|---|---|---|
| 主数据 | 老人、家属、员工、站点、设备、房间床位 | MySQL/PostgreSQL |
| 业务交易数据 | 呼叫单、工单、账单、排班、库存流水 | MySQL/PostgreSQL |
| 时序数据 | 心率、血压、睡眠、设备遥测 | 时序库或关系库分表 |
| 事件数据 | 告警事件、门禁事件、视频事件、通知任务 | MySQL + MQ + 检索引擎 |
| 非结构化数据 | 图片、报告、视频截图、附件 | 对象存储 |
| 检索数据 | 老人搜索、事件检索、日志检索 | Elasticsearch/OpenSearch |
| 缓存数据 | 会话、热点列表、规则缓存、站点配置 | Redis |

### 6.2 数据分层建议

建议按以下逻辑分层：

- ODS：原始接入层，保留设备原始数据和外部回调原文
- DWD：标准明细层，完成字段清洗、结构统一、主数据关联
- DWS：主题汇总层，按健康、呼叫、告警、运营等主题聚合
- ADS：应用数据层，面向看板、报表和专题分析输出

### 6.3 核心主数据设计

核心主数据对象包括：

- 老人主档
- 家属主档
- 员工主档
- 组织与站点主档
- 房间与床位主档
- 设备主档
- 服务项目主档

主数据由统一主数据中心维护，各业务服务引用主键与快照字段，不重复维护基础信息来源。

### 6.4 数据治理要求

- 敏感字段脱敏展示，如手机号、身份证号、住址、医疗信息。
- 所有核心写操作保留审计日志。
- 设备原始数据保留一定周期，过期后归档。
- 报表快照按日或月归档，满足追溯需求。
- 健康数据与告警数据保留周期应符合养老行业监管和项目方要求，建议在详细设计阶段进一步确认。

## 7. 技术架构

### 7.1 前端技术架构

| 终端 | 推荐技术 | 说明 |
|---|---|---|
| Web 管理后台 | React + TypeScript + 企业级 UI 组件库 | 适合复杂表格、工作台、看板 |
| 护理/运营移动端 | H5 或跨端框架 | 适合工单处理、告警处理、巡检 |
| 家属微信小程序 | 原生小程序或跨端框架 | 适合查询、通知、缴费、互动 |

前端通过统一网关接入，按角色、站点和数据权限控制页面能力。

### 7.2 后端技术架构

建议采用“Python 业务平台 + Go 实时接入”的混合架构：

- Python：FastAPI 或 Django 体系，用于业务 API、规则引擎、报表和后台服务。
- Go：Gin/Fiber 或标准库配合 MQTT/WebSocket 组件，用于高并发接入服务。
- 接口风格：以 REST 为主，实时通知场景支持 WebSocket，设备侧支持 MQTT/HTTP。
- 异步通信：使用消息队列进行事件解耦。

### 7.3 基础设施建议

- 数据库：MySQL 或 PostgreSQL
- 缓存：Redis
- 消息队列：RabbitMQ、Kafka 或云消息服务
- 搜索引擎：Elasticsearch/OpenSearch
- 对象存储：MinIO 或云 OSS
- 配置中心：Nacos、Consul 或基于 GitOps/环境变量方案
- 任务调度：Celery、APScheduler 或独立调度器

## 8. 集成架构

### 8.1 集成原则

- 所有外部系统和硬件通过适配层接入，不允许直接耦合到业务核心代码。
- 外部事件统一进入事件中心，形成标准事件模型。
- 对外部接口调用必须支持重试、幂等、超时和失败补偿。

### 8.2 集成对象

| 集成对象 | 接入方式 | 说明 |
|---|---|---|
| 智能穿戴设备 | MQTT/HTTP/SDK | 接收健康数据、设备状态、绑定信息 |
| 呼叫按钮/主机 | TCP/HTTP/厂商协议 | 采集紧急呼叫事件 |
| 视频监控平台 | SDK/HTTP/Webhook/GB28181 对接层 | 接收跌倒、闯入等事件 |
| 门禁系统 | HTTP/SDK | 获取门禁开关记录、异常进入事件 |
| 短信/微信平台 | API | 发送通知与催办 |
| 支付平台 | API | 家属账单缴费与支付回调 |
| 地图定位服务 | API | 站点位置和服务可视化 |
| 监管平台 | API/文件交换 | 后续扩展预留 |

### 8.3 适配层设计

适配层建议包含：

- 协议适配器：协议转换、签名处理、字段映射
- 设备模型映射：将不同厂商设备统一映射为平台标准模型
- 回调验签模块：保证第三方回调可信
- 幂等处理模块：按事件 ID、设备流水号或请求签名去重
- 重试补偿模块：处理外部接口临时失败

## 9. 安全架构

### 9.1 身份与认证

- 平台内部用户采用统一身份认证，支持账号密码、短信验证码和后续单点登录扩展。
- 家属端采用手机号+验证码或微信授权登录。
- 设备接入采用设备证书、设备密钥或白名单认证。

### 9.2 权限控制

采用“用户 - 角色 - 组织/站点 - 数据范围”四维权限模型。

- 功能权限：控制菜单、按钮、接口
- 数据权限：控制可查看的站点、老人、工单和报表数据
- 场景权限：例如护理员仅能处理本班次、本区域任务

### 9.3 数据安全

- 传输层使用 HTTPS/TLS
- 敏感字段加密存储或脱敏展示
- 日志中不记录明文密码、令牌、身份证号全量信息
- 支付回调、设备回调、第三方接口启用验签和时间戳校验

### 9.4 审计与合规

- 登录、登出、权限变更、数据导出、账单操作、告警处置等关键行为留痕
- 审计日志不可随意篡改
- 对健康数据、身份信息、联系方式等敏感信息设置访问审批或最小授权策略

## 10. 部署架构

### 10.1 一期部署建议

一期推荐采用容器化部署，环境分为：

- 开发环境
- 测试环境
- 预生产环境
- 生产环境

### 10.2 部署模式

#### 方案 A：模块化单体起步

适用于一期快速交付：

- 核心业务服务部署为一个 Python 平台服务
- IoT 接入、实时推送等高并发部分独立为 Go 服务
- Redis、数据库、对象存储、消息队列独立部署

优点：

- 开发复杂度低
- 交付速度快
- 运维成本较可控

风险：

- 后续部分模块扩展时需逐步拆分

#### 方案 B：微服务化演进

适用于二期后业务增长：

- 按业务域拆分多个独立服务
- 引入服务注册发现、统一配置、链路追踪
- 建立独立 CI/CD 和灰度发布流程

### 10.3 站点与边缘接入

对于视频监控和部分门禁设备，建议保留边缘接入能力：

- 站点边缘网关负责本地设备协议接入
- 平台接收标准化事件与状态数据
- 网络异常时边缘侧可短期缓存和补传

## 11. 可观测性与运维架构

### 11.1 日志

- 应用日志：记录服务运行状态和错误
- 访问日志：记录接口调用、耗时、状态码
- 审计日志：记录用户关键操作
- 设备日志：记录设备接入、心跳、断线重连、异常消息

### 11.2 监控指标

- 接口 QPS、成功率、耗时
- 呼叫响应时长、闭环时长
- 健康数据上传成功率
- 设备在线率
- 告警数量、告警积压量、告警处置时长
- 消息发送成功率
- 数据库和缓存资源使用率

### 11.3 链路追踪

对以下关键链路进行追踪：

- 设备上报到业务入库
- 呼叫事件到工单闭环
- 视频告警到通知推送
- 家属缴费到支付回调

### 11.4 运维保障

- 支持健康检查接口
- 支持自动告警和值班通知
- 支持定时备份和恢复演练
- 支持灰度发布和快速回滚

## 12. 高可用与容灾设计

### 12.1 高可用设计

- API 网关和核心服务多实例部署
- Redis、消息队列、数据库采用主从或高可用方案
- 核心业务异步解耦，防止局部故障扩散
- 对呼叫和告警场景设置优先级队列

### 12.2 容灾设计

- 数据库按日备份、关键数据异地备份
- 对象存储多副本保存
- 核心配置纳入版本化管理
- 支持灾备环境或最小化应急恢复方案

### 12.3 降级策略

当部分依赖异常时，系统应支持：

- 非核心报表功能降级
- 第三方通知失败后改用替代通道
- 视频分析不可用时允许人工事件录入
- 设备实时流异常时按最后状态和人工巡检兜底

## 13. AI 与算法能力规划

### 13.1 一期建议能力

- 跌倒识别结果接入与事件联动
- 异常聚集识别结果接入
- 健康指标异常规则辅助判断
- 告警优先级辅助排序

### 13.2 架构位置

AI/算法能力建议作为独立能力层存在，不直接嵌入核心业务服务：

- 算法平台输出识别结果
- 平台事件中心接收结果并标准化
- 告警服务根据规则生成工单和通知

### 13.3 风险说明

- AI 结果不能直接替代人工判断
- 误报、漏报需要在流程上设计人工复核
- 算法结果和业务处置结果应沉淀，用于后续优化

## 14. 分阶段建设建议

### 14.1 一期

- 建设统一平台底座
- 完成老人档案、健康管理、服务呼叫、安防告警、运营管理、家属互动核心能力
- 完成关键设备与通知渠道接入
- 建立统一报表和审计能力

### 14.2 二期

- 增强监管平台对接
- 完善 AI 识别能力和风险画像
- 引入更精细的数据分析与服务推荐
- 逐步拆分服务，提升弹性与并发能力

## 15. 关键风险与规避建议

| 风险点 | 说明 | 规避建议 |
|---|---|---|
| 设备协议不统一 | 不同厂商接入难度高 | 建设标准设备模型和适配层 |
| 视频算法误报漏报 | 影响告警可信度 | 引入人工复核与规则二次过滤 |
| 多站点数据权限复杂 | 易出现越权和混乱 | 统一组织模型和数据权限模型 |
| 呼叫链路高峰拥堵 | 影响老人服务体验 | Go 独立承载实时链路并引入优先级队列 |
| 报表口径不一致 | 影响运营决策 | 建立统一指标定义和数据集市 |
| 明文凭据和隐私泄露 | 涉及重大安全问题 | 使用密钥管理、脱敏、审计和最小权限 |

## 16. 结论

本方案面向“1 个中心 + 31 个社区点位”的区域养老服务场景，采用“统一平台、分层解耦、混合技术栈、分期演进”的总体设计思路。一期推荐以模块化单体为核心、配合 Go 实时接入服务的架构模式落地，在控制实施复杂度的同时，确保关键链路稳定可用，并为后续监管对接、AI 增强和微服务演进预留空间。

后续在进入详细设计阶段前，建议优先完成以下确认事项：

- 设备厂商及协议清单
- 视频平台与门禁平台接口能力
- 家属端支付与消息渠道选型
- 数据保留周期与监管要求
- 云资源或本地机房部署边界
