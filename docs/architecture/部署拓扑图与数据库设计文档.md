## 1. 文档说明

### 1.1 文档目标

本文档在 [Arch.md](/Users/baizhiwen/MICROWARE/Git/RegionalHealthPlatform/docs/architecture/Arch.md) 基础上，细化一期系统的部署拓扑、环境规划、中间件布局、网络分区和数据库设计，为实施部署、资源申请、数据库建模和运维规划提供依据。

### 1.2 设计范围

## 2. 部署目标与约束

### 2.1 一期部署目标

- 支撑 1 个龙湖邻里中心和 31 个社区点位统一接入
- 满足核心业务 7x24 稳定运行
- 保证呼叫、告警、健康数据链路优先可用
- 支撑后续平滑扩容与服务拆分

### 2.2 一期设计约束

- 优先控制系统复杂度，避免过度微服务化
- 可采用云上或混合部署
- 视频分析与部分门禁接入可能存在边缘节点
- 第三方厂商协议多样，接入链路需独立隔离

## 3. 环境规划

| 环境 | 目标 | 部署特点 |
|---|---|---|
| 开发环境 | 日常开发与本地联调 | 轻量化，可共享中间件 |
| 测试环境 | 集成测试、接口联调 | 与生产相似但规模较小 |
| 预生产环境 | 上线前验证、压测、发布演练 | 配置尽量接近生产 |
| 生产环境 | 正式运营 | 高可用、监控完善、可回滚 |

## 4. 总体部署拓扑

### 4.1 一期推荐部署拓扑

```text
                         +---------------------------+
                         |        用户访问层         |
                         | Web / Mobile / 小程序 / 大屏 |
                         +-------------+-------------+
                                       |
                                 HTTPS / WSS
                                       |
                    +------------------v------------------+
                    |         访问接入与安全层            |
                    | SLB / WAF / API Gateway / Ingress   |
                    +------------------+------------------+
                                       |
          +----------------------------+----------------------------+
          |                                                         |
+---------v---------+                                     +---------v---------+
|   Python 平台区    |                                     |   Go 实时接入区    |
| user/elder/health |                                     | iot/call/ws       |
| ops/billing/family|                                     | device adapter    |
| report/message    |                                     | realtime push     |
+---------+---------+                                     +---------+---------+
          |                                                         |
          +----------------------------+----------------------------+
                                       |
                         +-------------v-------------+
                         |      事件与中间件层       |
                         | Redis / MQ / Scheduler    |
                         +------+------+-------------+
                                |      |
          +---------------------+      +----------------------+
          |                                                |
+---------v---------+                           +----------v-----------+
|   关系型数据库区   |                           |    检索与对象存储区   |
| MySQL/PostgreSQL  |                           | ES / MinIO / OSS     |
+-------------------+                           +----------------------+


站点边缘侧：

  穿戴设备 / 呼叫按钮 / 门禁 / 摄像头
                |
           边缘网关或厂商平台
                |
         HTTPS / MQTT / Webhook
                |
            平台接入区
```

### 4.2 拓扑说明

- 用户统一通过网关访问，网关承担鉴权、限流、审计入口能力。
- Python 平台区承载后台业务主服务。
- Go 实时接入区承载 IoT 接入、呼叫事件和 WebSocket 推送。
- Redis、消息队列、调度器构成事件与中间件层。
- 数据库、搜索、对象存储分区部署，避免互相影响。
- 站点设备优先通过边缘网关或厂商平台进行协议收敛。

## 5. 网络与安全分区建议

### 5.1 分区建议

| 区域 | 说明 | 是否直接暴露公网 |
|---|---|---|
| DMZ 接入区 | WAF、SLB、API Gateway | 是 |
| 应用服务区 | Python 服务、Go 服务 | 否 |
| 数据服务区 | DB、Redis、MQ、ES、对象存储 | 否 |
| 运维管理区 | 堡垒机、监控、日志、CI/CD Runner | 否 |
| 边缘接入区 | 设备网关、视频接入节点 | 视网络方案而定 |

### 5.2 网络控制要求

- 应用服务区不得直接暴露数据库端口到公网
- 运维操作通过堡垒机或安全通道进行
- 第三方回调入口单独验签与白名单控制
- 设备接入链路单独监控，避免异常流量冲击业务区

## 6. 服务部署设计

### 6.1 Python 服务部署建议

建议拆分为以下逻辑服务，可在一期按模块化单体部署：

| 服务名 | 核心职责 | 推荐部署方式 |
|---|---|---|
| `platform-app` | 用户、档案、健康、运营、账单、家属服务 | 多实例容器 |
| `message-worker` | 短信、微信、通知异步处理 | Worker 容器 |
| `report-worker` | 报表汇总、定时任务 | Worker 容器 |
| `rule-engine-worker` | 健康预警、超时升级、规则计算 | Worker 容器 |

### 6.2 Go 服务部署建议

| 服务名 | 核心职责 | 推荐部署方式 |
|---|---|---|
| `iot-access` | 设备注册、心跳、数据接入 | 多实例容器 |
| `call-realtime` | 呼叫事件接入和分发 | 多实例容器 |
| `event-push` | WebSocket 推送 | 多实例容器 |
| `adapter-service` | 门禁/视频/厂商协议适配 | 按厂商或协议拆分 |

### 6.3 中间件部署建议

| 组件 | 用途 | 建议 |
|---|---|---|
| Redis | 缓存、会话、分布式锁、短期状态 | 主从或哨兵 |
| MQ | 事件解耦、异步通知、回调处理 | RabbitMQ 或 Kafka |
| MySQL/PostgreSQL | 主业务数据存储 | 主从或高可用 |
| Elasticsearch/OpenSearch | 检索与日志查询 | 生产双节点以上 |
| MinIO/OSS | 报告、图片、截图、附件 | 多副本 |

## 7. 容量与扩展建议

### 7.1 一期容量关注点

- 设备并发上报数量
- 呼叫高峰瞬时事件量
- 视频告警回调频次
- 家属端高峰查询与缴费
- 报表汇总任务对数据库的冲击

### 7.2 扩展策略

- Python 平台服务按实例水平扩展
- Go 接入服务按连接数和事件量水平扩展
- 报表与规则任务独立 Worker 扩展
- 搜索、对象存储与 MQ 独立扩展

## 8. 备份、容灾与回滚

### 8.1 备份策略

| 对象 | 备份方式 | 频率 |
|---|---|---|
| 主数据库 | 全量 + Binlog | 全量每日，日志实时 |
| 对象存储 | 多副本或跨区复制 | 按策略执行 |
| 配置与脚本 | Git 管理 + 制品归档 | 每次发布 |
| 索引数据 | 可重建 + 周期快照 | 每日 |

### 8.2 回滚策略

- 应用版本采用镜像版本号管理
- 数据库变更采用可回滚迁移脚本
- 发布采用灰度或分批发布
- 回调链路变更需保留旧协议兼容窗口

## 9. 数据库设计总览

### 9.1 数据库选型建议

一期建议采用 MySQL 或 PostgreSQL 作为核心关系型数据库，辅以 Redis、对象存储和检索引擎。

建议划分以下逻辑库：

| 逻辑库 | 说明 |
|---|---|
| `rhp_core` | 用户、组织、权限、基础主数据 |
| `rhp_elder` | 老人档案、家属关系、床位与入住信息 |
| `rhp_health` | 健康记录、预警、设备绑定 |
| `rhp_call` | 呼叫单、响应记录、超时升级 |
| `rhp_alert` | 安防告警、门禁事件、处置记录 |
| `rhp_ops` | 员工、排班、考勤、物资、餐饮、工单 |
| `rhp_finance` | 账单、支付、对账 |
| `rhp_msg` | 消息通知、模板、发送记录 |
| `rhp_audit` | 审计日志、接口日志、导出记录 |

一期物理上可先落在同一个实例中，逻辑上按 schema 或命名空间隔离。

## 12. 分表与归档建议

### 12.1 建议优先考虑分表的对象

- `health_metric_record`
- `call_order`
- `alert_event`
- `audit_log`
- `message_task`

### 12.2 分表维度建议

- 健康记录按月分表
- 日志和消息按月分表
- 告警与呼叫按季度或按量分表

### 12.3 归档策略

- 原始设备数据保留在线 6 到 12 个月，之后归档
- 审计日志长期留存，冷热分层
- 报表快照按月归档

## 14. 数据安全设计

### 14.1 加密与脱敏

- 身份证号、手机号、住址、支付信息建议加密存储
- 查询展示时按角色脱敏
- 审计和日志中禁止打印明文凭据与隐私数据

### 14.2 数据权限

- 按组织、站点、班组、家属授权关系控制数据可见范围
- 导出操作单独审计

## 15. 建库建表实施建议

### 15.1 实施顺序

1. 先建基础组织、用户、站点、房间、床位、员工表
2. 再建老人、家属、设备、健康、呼叫、告警表
3. 再建运营、账单、消息、审计表
4. 最后增加索引、归档表、汇总表

### 15.2 命名规范

- 表名前缀统一按业务域规划
- 主键统一 `id`
- 时间字段统一 `created_at`、`updated_at`
- 状态字段统一 `status`
- 编号字段统一 `*_no`

## 16. 结论

一期部署建议采用“统一接入层 + Python 平台业务区 + Go 实时接入区 + 独立中间件与存储层 + 可选边缘接入”的拓扑模式，兼顾交付速度和后续扩展能力。

数据库设计建议优先围绕老人主档、健康记录、呼叫单、安防告警、员工排班、账单支付、消息通知和审计日志构建核心模型，并从一期开始同步考虑幂等、索引、分表、归档和脱敏要求，避免后期返工。
